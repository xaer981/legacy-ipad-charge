# Phase 0 — техническая осуществимость

**GO для лабораторного опыта с фильтром.** В ВМ iPad 2 принял команду Apple и поднял распознанный лимит с 500 до 1000 мА. Откат восстановил 500 мА. [Результат опыта](#запрос-до-1-а-и-откат)

**NO-GO для выпуска варианта без фильтра на текущем этапе.** На штатном стеке при активном USB-сеансе второго экрана `CreateFileW` вернул `ERROR_NOT_SUPPORTED` при открытии Apple WinUSB-интерфейса `MI_01`. Доставка стандартного запроса и vendor-запроса через этот интерфейс остаётся неподтверждённой.

## Что подтверждено на Windows 11

Снимок от 17 ноября 2026 года получен через `inspect --vid 05AC --pid 12A2`, `probe --dry-run`, `Get-PnpDeviceProperty` и чтение установленного INF Apple. На `05AC:12A2` активна конфигурация `3`, скорость High-Speed. Путь от root hub проходит через порты `10 → 1` и хаб `05E3:0608`. Все три узла были запущены, PnP не сообщал о проблемах.

| Узел | Служба / эффективный стек | Зарегистрированные интерфейсы |
|---|---|---|
| Физический USB-узел | `usbccgp` → `AppleLowerFilter` → `ACPI` → `USBHUB3` | `a5dcbf10-6530-11d2-901f-00c04fb951ed` |
| `MI_00` | `WUDFWpdMtp` / `WpdUpFltr` → `WUDFRd` → `WINUSB` → `usbccgp` | `6ac27878-a6fa-4155-ba85-f98f491d4f33`, `6bdd1fc6-810f-11d0-bec7-08002be2092f` |
| `MI_01` — Apple USB Multiplexor | `WINUSB` / `AppleKmdfFilter` → `WUDFRd` → `WINUSB` → `usbccgp` | `664be590-54bd-4964-8a8c-6cd1314f6dc2`, `dee824ef-729b-4a0e-9c14-b7117d33a817`, `f0b32be3-6678-4879-9230-e43845d805ee` |

Пакет Apple версии `538.0.0.0` включает `winusb.inf` из секции AppleUsbMux и объявляет `664be590-54bd-4964-8a8c-6cd1314f6dc2` как интерфейс iTunes WinUSB. На `dee824ef-729b-4a0e-9c14-b7117d33a817` у `MI_01` подтверждено `DEVPKEY_DeviceInterface_Restricted=true`. Процесс Apple Mobile Device Service присутствовал. Эти измерения описывают данный стек и этот сеанс Windows.

## Варианты транспорта

| Подход | Вывод |
|---|---|
| **Win32 WinUSB, штатный `MI_01`** | `WinUsb_ControlTransfer` принимает device-recipient запрос через первоначальный интерфейсный handle. На текущем стеке при активном Apple Mobile Device Service и активном USB-клиенте проверка остановилась на `CreateFileW` с `ERROR_NOT_SUPPORTED`. Документация указывает сброс политик интерфейса при инициализации WinUSB и отсутствие поддержки одновременного доступа нескольких приложений. Точный драйвер, вернувший ошибку, и поведение без конкурирующего клиента остаются неизвестными. [ControlTransfer](https://learn.microsoft.com/en-us/windows/win32/api/winusb/nf-winusb-winusb_controltransfer) · [Initialize](https://learn.microsoft.com/en-us/windows/win32/api/winusb/nf-winusb-winusb_initialize) · [Сравнение моделей драйверов](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/winusb-considerations) |
| **WinUSB, `MI_00`** | `WINUSB` есть ниже WPD/MTP. У узла видны WPD/STI GUID, отдельный WinUSB interface в снимке отсутствует. Возможность прямого доступа через существующий интерфейс функции не подтверждена. |
| **`Windows.Devices.Usb`** | Работает через WinUSB и зависит от правил доступа WinRT. На штатном интерфейсе `MI_01` выставлено `Restricted=true`. Это наблюдение относится к WinRT. [Поддержка устройств](https://learn.microsoft.com/en-us/uwp/api/windows.devices.usb) |
| **libusb** | Windows-бэкенд перечисляет составные функции и пытается использовать поддерживаемый драйверный бэкенд функции. Он зависит от того же WinUSB-стека. Удаление явного `claim` из Linux-форка не переносит Linux-семантику на Windows. `UsbDk`, `libusbK` и `libusb0` потребовали бы драйверных изменений для этого эксперимента. [Windows backend](https://github.com/libusb/libusb/wiki/Windows) · [Диспетчеризация запросов](https://github.com/libusb/libusb/blob/master/libusb/os/windows_winusb.c) |
| **SetupAPI / Configuration Manager / USB Hub IOCTL** | Поддерживаемый путь инвентаризации. `IOCTL_USB_GET_NODE_CONNECTION_INFORMATION_EX` даёт активную конфигурацию, `EX_V2` уточняет SuperSpeed, а `IOCTL_USB_GET_DESCRIPTOR_FROM_NODE_CONNECTION` подставляет стандартный `GET_DESCRIPTOR`. [USBView](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/usbview) · [Поля запроса дескриптора](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/usbioctl/ns-usbioctl-_usb_descriptor_request) |
| **Apple Mobile Device / USBMUX** | Доступная модель сервиса мультиплексирует соединения к сервисам iOS. Публичного API Apple для отправки произвольного control transfer через этот сервис в рамках исследования не найдено. [libusbmuxd](https://github.com/libimobiledevice/libusbmuxd) |
| **UMDF/KMDF / WDM** | В драйверном контексте доступны WDF control requests или внутренние USB URB. Собственный подписанный фильтр остаётся гипотезой для отдельного стенда. Для него требуются выбор места в стеке, проверка подписи и HVCI и тесты параллельной работы с USBMUX. [WDF и WinUSB](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/usb-control-transfer) · [USB URB](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/communicating-with-a-usb-device) |

## Как трактовать Linux-референс

Обе утилиты формируют vendor OUT с получателем device. `mkorenkov/ipad_charge` захватывает интерфейс 0; `FD-/usb_charge` отправляет запрос после `libusb_open`, у него есть PID `0x12A2` и пара `500/1600` для iPad. В комментариях и README обозначения полей различаются. Драйвер Linux `apple-mfi-fastcharge` записывает один и тот же offset в оба поля, что согласуется с одной из опубликованных редакций Apple Accessory Design Guidelines. Ни один из этих источников сам по себе не устанавливает семантику и результат для iPad 2 с конкретной версией iOS 9. В коде есть только тестовый пакет со значениями из форка. [Исходный проект](https://github.com/mkorenkov/ipad_charge/blob/master/ipad_charge.c) · [Форк](https://github.com/FD-/usb_charge/blob/master/usb_charge.c) · [Ядро Linux](https://github.com/torvalds/linux/blob/master/drivers/usb/misc/apple-mfi-fastcharge.c) · [Редакция руководства Apple](https://device.report/m/43c52c90006a7915765a487127eb3f5d0f040f03b4c6d220d8e17ae2a4252804.pdf)

## Проверка `GET_STATUS`

17 ноября 2026 года на Windows 11, MSI MPG Z890 EDGE TI WIFI и iPad 2 `05AC:12A2` в конфигурации `3` инструмент `LegacyIpadCharge.GetStatusProbe` нашёл единственный Apple iTunes WinUSB-интерфейс `664be590-54bd-4964-8a8c-6cd1314f6dc2` на `MI_01`. `CreateFileW` с разделяемым чтением и записью и `FILE_FLAG_OVERLAPPED` вернул Win32 `50` (`ERROR_NOT_SUPPORTED`). До `WinUsb_Initialize` и `WinUsb_ControlTransfer` выполнение не дошло. Код `50` сам по себе не устанавливает, какой слой возвратил ошибку. [Коды ошибок Win32](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--0-499-)

До и после попытки совпали PnP-снимки, идентификатор USB-подключения iPad в `ListDevices`, процесс Apple Mobile Device Service и наблюдаемое TCP-соединение клиента второго экрана с USBMUX. Содержание изображения на iPad в проверку не входило.

## Проверка KMDF-фильтра в VirtualBox

На гостевой Windows 11 `26100.1742` с пакетом Apple `552.0.0.0` iPad показывал рабочий стол гостя как второй экран по USB. Перед установкой фильтра сделали снимок ВМ.

Windows приняла экспериментальный Extension INF `LegacyIpadStatus.inf` версии `0.1.0.0` как `oem4.inf`. После холодного запуска ВМ и подключения iPad родительский узел `05AC:12A2` сохранил базовый INF Apple `oem3.inf`, но получил Code 37 (`CM_PROB_FAILED_DRIVER_ENTRY`) со статусом `0xC000000D` (`STATUS_INVALID_PARAMETER`). Событие Kernel-PnP 219 названо для `LegacyIpadStatus` и содержит `0xC0000365` (`STATUS_FAILED_DRIVER_ENTRY`). Служба фильтра осталась `Stopped`. Диагностический интерфейс не появился, соединение клиента с USBMUX не установилось. Отправка `GET_STATUS` не состоялась. Источник `STATUS_INVALID_PARAMETER` в последовательности инициализации фильтра пока неизвестен. [Описание Code 37](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/cm-prob-failed-driver-entry)

После удаления `oem4.inf` в гостевой Windows и повторного проброса iPad все три узла устройства вернулись в `OK`, а клиент второго экрана восстановил TCP-соединение со службой Apple на `127.0.0.1:27015`. Повторную визуальную проверку изображения на iPad после отката не проводили.

Версия `0.1.0.1`, собранная штатным `WindowsKernelModeDriver10.0` с PDB, загрузилась в той же ВМ при включённой отладке ядра. `kd` остановился в `FxDriverEntry`, `DriverEntry` и `AddFilter`. `DriverEntry` и `AddFilter` вернули `STATUS_SUCCESS`. После возобновления ВМ служба фильтра была `Running`, диагностический интерфейс появился, все USB-узлы iPad остались в `OK`, и клиент второго экрана подключился к USBMUX. Вызов `--check` без повышенных прав вернул Win32 `5`, что согласуется с SDDL диагностического интерфейса. По сравнению с первой попыткой изменились способ сборки и режим отладки гостевой ОС, поэтому первопричина старого Code 37 пока не выделена.

При активной передаче изображения на iPad скрипт выполнил один стандартный `GET_STATUS` через фильтр. `IpadStatusProbe.exe` получил два байта со значением `0x0000`. После запроса TCP-соединение клиента второго экрана со службой Apple было `ESTABLISHED`. Пользователь подтвердил, что изображение вернулось после короткого разрыва, и заметил похожее поведение до команды. `kd` фиксировал тайм-ауты `AppleUsbFilter` в ходе эксперимента. В журнале VirtualBox после последнего проброса отсутствует отсоединение USB со стороны гипервизора. Эти наблюдения не устанавливают причину разрыва. По окончании диагностики `kd` отсоединён через `qd`, гостевая Windows продолжила работу. Измерения тока и проверка команд зарядки в этот опыт не входили.

В контрольном запуске гостевая Windows загрузилась с `debug No`, тестовая подпись сохранилась, виртуальный COM1 выключен. `LegacyIpadStatus` запустился и iPad был проброшен в ВМ. Изображение сначала появилось, затем пропало по наблюдению пользователя. `GET_STATUS` и команды зарядки в этом запуске не вызывались. В течение последующих 180 секунд ни одна из 37 выборок с интервалом пять секунд не показала `ESTABLISHED` для соединения клиента второго экрана с USBMUX на `127.0.0.1:27015`. Служба Apple слушала порт, фильтр и служба Apple оставались `Running`, узлы iPad были в `OK` в начале и конце замера. VirtualBox не зарегистрировал отсоединение USB. Для локализации причины нужен контроль в той же ВМ с удалённым тестовым фильтром.

После удаления `LegacyIpadStatus.inf` версии `0.1.0.1` и повторного проброса iPad в той же ВМ родительский узел использовал `oem3.inf` и стек `usbccgp` → `AppleLowerFilter`. Все три USB-узла были в `OK`, служба фильтра осталась `Stopped`. В течение 180 секунд все 37 выборок показали одно и то же соединение клиента второго экрана с USBMUX в состоянии `ESTABLISHED`. Этот замер начался сразу после переподключения с активным сеансом. Замер с фильтром начался после исчезновения изображения. Для проверки причинной связи нужны два запуска с одинаковым моментом начала наблюдения и одинаковой процедурой подключения. В этом запуске ручные USB-запросы не выполнялись.

При повторной установке `0.1.0.1` в той же ВМ iPad отсоединили до `pnputil /add-driver ... /install`. Windows установила пакет `oem4.inf` для iPad и не потребовала перезапуска. После повторного проброса, при `debug No`, убедились, что фильтр `Running` и клиент подключён к USBMUX. С этого момента за 180 секунд все 37 выборок показали одно и то же TCP-соединение `ESTABLISHED`, как и в опыте без фильтра. В конце все три USB-узла были в `OK`, а стек `usbccgp` включал `LegacyIpadStatus` и `AppleLowerFilter`. Устойчивый разрыв из первого запуска в этом трёхминутном окне не воспроизвёлся. Изображение на iPad отдельно не подтвердили. Ручные USB-запросы не выполнялись.

Версия `0.1.0.2` заменяет `WdfUsbTargetDevice` на прямую отправку одного `URB_FUNCTION_GET_STATUS_FROM_DEVICE`. ВМ штатно выключили и запустили с отсоединённым iPad после добавления `oem5.inf`. После проброса `LegacyIpadStatus` был `Running`, а SHA-256 файла из пути службы совпал со сборкой `0.1.0.2`. В привязке родительского узла `pnputil` по-прежнему показывал Extension INF `oem4.inf`.

В первом наблюдении с `0.1.0.2` пользователь увидел рабочий стол гостя на iPad, затем изображение пропало до запуска тестового скрипта. После подключения агента все 83 последующие выборки показали одно и то же TCP-соединение с USBMUX. Все три USB-узла остались в `OK`, новых событий UMDF 10110/10111 и отсоединения iPad в журнале VirtualBox не было. Маркер запуска и файл результата отсутствовали. Этот эпизод показывает, что изображение может пропасть до ручного `GET_STATUS` при открытом TCP-соединении. Причина разрыва изображения неизвестна.

Два переподключения через VirtualBox восстанавливали TCP-сеанс. После обоих изображение снова пропадало до подтверждения `Y`, в том числе при уже открытой повышенной консоли. Скрипт дошёл до `choice` после успешного `--check`, который только открывает диагностический интерфейс. Маркер и результат `--run-once` так и не появились. Гостевая Windows за время сеанса зарегистрировала три события UMDF `10111` для Apple Mobile Device USB Device с соответствующими отчётами WER `WUDFHostProblem2` (`HostTimeout`, `appleusbfilter.dll`). В одном наблюдении TCP-сеанс закрылся в пределах секунды после `10111`. В этом сеансе `GET_STATUS` не отправлялся. Следующий контроль — сравнить работу изображения и события UMDF в одинаковом окне наблюдения на штатном гостевом стеке и с `0.1.0.2`, без ручных USB-запросов. К одному прямому `GET_STATUS` можно вернуться при устойчивом изображении.

### Сравнение штатного стека с `0.1.0.2`

17 ноября 2026 года в той же ВМ сначала экспортировали и удалили оба пакета `LegacyIpadStatus`, затем провели три минуты наблюдения со штатным стеком `usbccgp` → `AppleLowerFilter`. Для второй серии установили только `0.1.0.2` через `pnputil /add-driver … /install`. После проброса подтвердили Extension INF `oem4.inf`, службу `Running` и SHA-256 установленного SYS. Предварительный запуск после одного лишь добавления пакета в Driver Store исключили, поскольку фильтр ещё отсутствовал в стеке.

Оба окна начались с первого перехода TCP-соединения клиента второго экрана с USBMUX в `ESTABLISHED` на `127.0.0.1:27015`. За 180 секунд в каждом окне сняли 177 выборок с интервалом примерно в секунду.

| Стек в ВМ | Разрыв от начала окна | Выборки с `ESTABLISHED` | События UMDF `10111` | Отчёты WER `HostTimeout` для `appleusbfilter.dll` |
| --- | ---: | ---: | ---: | ---: |
| Штатный Apple | 77,9 с | 76/177 | 2 | 4 |
| Apple с `LegacyIpadStatus 0.1.0.2` | 89,7 с | 87/177 | 2 | 4 |

В обоих прогонах первое событие `10111` предшествовало первой выборке без TCP-соединения менее чем на секунду по времени журнала гостя. Соединение само не восстановилось до конца наблюдения. VirtualBox не зарегистрировал отсоединения iPad во время окон, а в конце все три узла iPad были в `OK`. Ручные USB-запросы не выполнялись. Изображение на самом iPad в рамках этих окон отдельно не подтверждено.

Разрыв воспроизвёлся со штатным стеком в VirtualBox. Два прогона не устанавливают первопричину тайм-аута и не позволяют оценить влияние фильтра на частоту разрывов. Влияние прямого `GET_STATUS` остаётся непроверенным.

### Контроль на хосте

18 ноября 2026 года `Legacy iPad Lab` оставалась выключенной. iPad был подключён напрямую к Windows-хосту через контроллер Intel xHCI. Хост использовал драйвер Apple `538.0.0.0`, а в предыдущих прогонах в госте использовались `552.0.0.0` и виртуальный EHCI. Пользователь подтвердил, что видел рабочий стол хоста на iPad и изображение не пропадало.

С 10:36 до 10:39 по Москве во всех 176 выборках сохранялось одно TCP-соединение клиента второго экрана с USBMUX. Соединение было открыто с 10:31:59. Новых событий UMDF `10110`/`10111` для Apple и отчётов WER `HostTimeout` для `appleusbfilter.dll` не было. В конце все три USB-узла iPad были в `OK`. Настройки и драйверы хоста не менялись, ручные USB-запросы не выполнялись.

Разрыв на хосте в этом окне не воспроизвёлся. Контроль не изолирует USB-проброс от различий ОС и версий драйвера Apple. Следующее сравнение в той же ВМ — штатный стек Apple `552.0.0.0` на виртуальном xHCI против прежнего результата на EHCI, без тестового фильтра и ручных USB-запросов.

### Штатный стек Apple на виртуальном xHCI

18 ноября 2026 года в `Legacy iPad Lab` заменили виртуальные OHCI/EHCI на xHCI. При отсоединённом iPad удалили пакет `LegacyIpadStatus 0.1.0.2`. После проброса проверили контроллер xHCI в цепочке устройства, штатные `usbccgp` и `AppleLowerFilter`, Apple `552.0.0.0` и отсутствие службы тестового фильтра. VirtualBox зарегистрировал подключение iPad на HighSpeed.

По наблюдению пользователя, рабочий стол гостя был виден на iPad несколько секунд. TCP-сеанс клиента второго экрана с USBMUX оставался открыт 82,2 секунды от начала окна и был виден в 80 из 176 выборок за три минуты. Событие UMDF `10111` для Apple Mobile Device USB Device предшествовало первой выборке без TCP менее чем на секунду. WER записал два отчёта `HostTimeout` для `appleusbfilter.dll`. Соединение само не восстановилось. Все три узла iPad были в `OK` в конце, и VirtualBox не зарегистрировал отсоединения во время окна.

Замена EHCI на xHCI не устранила разрыв. Краткий визуальный сбой произошёл раньше разрыва TCP и не измеряется по состоянию сокета. Причина тайм-аута Apple пока неизвестна. ## Критерий пересмотра

Следующий диагностический опыт можно провести на отдельном стенде с тем же пакетом Apple. Сравнить результат `CreateFileW` при активном USBMUX и без конкурирующего клиента. Это поможет выяснить, связан ли отказ с состоянием сеанса. Если интерфейс открывается, проверить `WinUsb_Initialize` и видимость стандартного device-recipient IN-запроса на USB-линии. После этого для vendor OUT и реакции iPad потребуется отдельный эксперимент. Электрическая пригодность источника остаётся независимым условием эксперимента с повышением тока.
